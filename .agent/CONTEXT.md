## 1. Propósito del Sistema
**HouseMatch** es una herramienta automatizada multi-tenant diseñada para capturar pedidos de propiedades en grupos de WhatsApp de agentes inmobiliarios (Tucumán, Argentina), extraer sus intenciones y características mediante modelos de lenguaje (LLM), y cruzarlos inteligentemente con una cartera local de propiedades en Supabase. Los matches calificados son notificados de forma consolidada por WhatsApp (cada 10 min) y se gestionan desde un Dashboard interactivo securizado por IP-Binding.

## 2. Esquema de Base de Datos Actualizado (Supabase Multi-Tenant) — v2

Los agentes deben respetar de forma estricta la existencia de la clave foránea `tenant_id` en todas las operaciones de lectura/escritura. El esquema fue migrado a inglés en SPEC-0012 con soporte PostGIS. La tabla `Message` fue eliminada — sus datos se embeben en `match_queue`.

* **`profiles`** *(ex `Tenant`)*: `id` (UUID, PK), `full_name`, `email`, `created_at`. **Corrección de drift (KAN-64, 2026-07-29):** los campos `associated_ip`/`ip_bound_at`/`otp_code`/`otp_expires_at` que esta sección documentaba desde SPEC-0012 ya no existen — quedaron eliminados en algún punto posterior a SPEC-0013 (magic link reemplazó el login por OTP de WhatsApp) sin que esta doc se actualizara; confirmado por introspección real de columnas, no había ninguna migración que los recreara. **Campos nuevos (KAN-64, pivot a matching 100% web):** `phone_number` (ahora el teléfono personal del agente, no el JID del bot de WhatsApp), `agency_name`, `city`, `country`, `profile_completed` (boolean, default `false`). Se completan vía `POST /api/profile` después del primer login por magic link — `POST /api/auth/exchange-token` sigue creando la fila con solo `id`/`email`/`full_name` (ver sección 3), el resto queda `null` hasta que el agente complete su perfil. (Límite estricto de 10 tenants).
* **`properties`** *(ex `Property`)*: `id` (UUID, PK), `tenant_id` (FK, NOT NULL), `address`, `floor`, `unit`, `block`, `lot`, `price`, `currency`, `maintenance_fees`, `bedrooms`, `features`, `contact_info`, `operation`, `property_type`, `sheet_name`, `latitude`, `longitude`. **Nota:** `zone_display_name` es campo runtime-only en TypeScript — NO se persiste en BD.
* **`match_queue`** *(ex `Match`, absorbe ex `Message`)*: `id` (UUID, PK), `tenant_id` (FK, NOT NULL), `property_id` (FK, NOT NULL), `is_notified` (Boolean, NOT NULL, default `false`), `created_at` (timestamptz), `score`, `validation_score`, `is_valid` (Boolean), `reasoning`, `match_details`, `user_review_status` ('PENDING' | 'ACCEPTED' | 'REJECTED'), `feedback_reason`. Campos de mensaje embebidos: `whatsapp_group_name`, `whatsapp_sender_name`, `whatsapp_sender_phone`, `raw_message_text`. **Corrección (2026-07-02):** columnas reales confirmadas por introspección directa vía MCP de Supabase — no existen `notification_status` ni `fecha` (drift de esta misma documentación, nunca existieron en la base; el código siempre usó `is_notified`/`created_at`). DDL completo en `docs/evolucion_proyecto/schema_actual.sql`.
* **`whatsapp_sessions`** — **ELIMINADA (KAN-64, 2026-07-29):** guardaba `auth_creds` (JSONB) de Baileys, single-row por tenant (patrón de SPEC-0012). Dropeada junto con el enum `whatsapp_session_status` como parte del pivot a matching 100% web (ver entry de KAN-64 en sección 5) — confirmado 0 filas antes de dropear, sin pérdida de datos reales. **Actualización (retiro de código muerto, 2026-07-29, ver entry en sección 5):** `src/services/whatsapp.ts` y `src/services/supabaseAuth.ts` (el código muerto que referenciaba esta tabla) ya fueron borrados del repo, junto con `sessionCleanup.ts` y `notifier.ts` — no quedan referencias vivas ni muertas a `whatsapp_sessions` en `src/`.
* **`active_searches`** *(KAN-35, 2026-07-28)*: `id` (UUID, PK), `tenant_id` (FK -> `profiles.id`, NOT NULL), `criteria` (jsonb, NOT NULL default `{}`), `raw_text` (text, NOT NULL), `status` (text, NOT NULL default `'active'`, CHECK IN `active`/`expired`/`matched`/`cancelled`), `created_at` (timestamptz), `expires_at` (timestamptz, NOT NULL). Índices por `tenant_id` y por `status`. `expires_at` se autocompleta vía trigger `set_active_searches_expires_at` (`created_at + 7 días`) solo si no se pasa explícito al insertar — no puede resolverse con un DEFAULT de columna. RLS con la misma política `tenant_id = auth.uid()` del resto de tablas tenant-scoped. Almacena las búsquedas activas de un tenant para el matching ciego (feature/matching-ciego, KAN-33). Primer código consumidor: `POST /api/search` (KAN-37, ver sección 3 y 5) inserta en esta tabla; `criteria` guarda el `ExtractedRealEstateRequest` tal cual devuelve `extractFromTextInput`. Detalle completo en `docs/evolucion_proyecto/schema_actual.sql`.

**Auth:** Implementada con Supabase Auth magic link (SPEC-0013). Flujo: email → magic link → `#access_token` en URL hash → `POST /api/auth/exchange-token` → cookie HttpOnly `housematch_session`. Middleware `tenantAuthMiddleware` valida via `supabase.auth.getUser(token)`, retorna 401 si inválido. Rate limit 5 req/min/IP en `request-magic-link`. **Patrón "Tenant Context" (KAN-63, 2026-07-28):** `req.supabaseClient` (usado por `GET/POST /api/matches`, `/api/matches/:id/feedback`, `/api/notifications/subscribe` y `/api/upload` vía `syncPropertiesToDatabase`) queda scoped al tenant real (`getTenantClient(token)`: anon key + el propio `access_token` del usuario como Bearer), no al cliente service-role — RLS ahora se aplica de verdad en cada request autenticado del dashboard, no solo como defensa en profundidad teórica. Los procesos de fondo sin sesión de usuario (`coordinator.ts`, `notifier*.ts`, `sessionCleanup.ts`, arranque en `main()`) siguen usando el cliente service-role a propósito — no tienen un tenant autenticado del que colgar un JWT.

## 3. Arquitectura del Código y Estructura de Archivos

La aplicación está construida sobre **Node.js** utilizando **TypeScript** y el gestor de paquetes **pnpm**.

* `src/index.ts`: Punto de entrada del sistema. Inicializa el servidor Express. **Desde KAN-64 (2026-07-29) ya NO levanta sesiones de Baileys**: `main()` precarga el catálogo en memoria de cada tenant iterando `profiles` (antes iteraba `whatsapp_sessions`, tabla eliminada). **Retiro completo (2026-07-29, ver entry en sección 5):** `GET /api/status` y `GET`/`POST /api/groups` fueron eliminados (sin reemplazo — el dashboard ya no gestiona conexión/grupos de WhatsApp); `src/services/whatsapp.ts`, `sessionCleanup.ts`, `supabaseAuth.ts` y `notifier.ts` (canal WhatsApp) fueron borrados del repo, no solo dejados de invocar.
* `src/services/coordinator.ts`: **Caché en memoria por tenant** (catálogo cargado vía Excel/Sheets + últimos matches conocidos como fallback de `GET /api/matches`). **Retiro completo (2026-07-29):** `handleIncomingMessage` (el pipeline de ingesta disparado por mensajes entrantes de WhatsApp — extracción, geolocalización, matching y persistencia en `match_queue`) se borró junto con `PipelineContext`; nunca se invocaba en producción (nada llamaba a `initTenantSession`, el único punto que lo hubiera disparado). El matching en vivo es 100% vía `active_searches`/`blindMatching.ts` (ver más abajo). `setCatalog`/`getCatalog`/`getRecentMatches` son lo único que queda.
* `src/services/ai.ts`: Implementa el patrón **Strategy** para proveedores de IA.
    * *Google Gemini Strategy (`gemini-2.5-flash-lite`)*: Modelo principal por costo y velocidad.
    * *OpenAI Strategy (`gpt-4o-mini`)*: Fallback dinámico automático configurado obligatoriamente con **Structured Outputs** (`json_schema`).
    * *Sub-Agentes Cognitivos:* **Agente 1 (Extractor)** con blindaje XML wrappers, **Agente 2 (Geolocalizador)** normalizador de zonas de Tucumán, y **Agente 3 (Validador)** filtro cualitativo de falsos positivos.
    * *KAN-36:* el Agente 1 tiene dos entry points públicos con el mismo schema de salida (`ExtractedRealEstateRequest`): `extractFromWhatsApp` (ex `extractRealEstateRequest`, sin cambios de comportamiento) y `extractFromTextInput` (texto libre de formulario para matching ciego, wrapper `<USER_TEXT>` y prompt propio `SYSTEM_INSTRUCTIONS_AGENT1_TEXT_INPUT`), detrás de `FREE_TEXT_EXTRACTION_ENABLED` (default `false` — no afecta a `extractFromWhatsApp`).
* `src/services/notifier-email.ts` *(SPEC-0014)*: **Único canal de notificación desde el retiro de WhatsApp (2026-07-29)** — antes convivía detrás de `NOTIFICATION_CHANNEL` con `src/services/notifier.ts` (canal WhatsApp, borrado). Corre cada `NOTIFICATION_INTERVAL_MINUTES` (default 20), consolida por tenant/grupo, envía por email vía Resend a `profiles.email`, con deep links `wa.me` trackeados (pixel de apertura + redirect de click, columnas `email_opened_at`/`email_clicked_at` en `match_queue`).
* `src/utils/matcher.ts`: Motor de coincidencia refactorizado bajo el patrón **Strategy**. Ejecuta 7 estrategias secuenciales (`Operation`, `PropertyType`, `Country`, `Zone`, `Bedrooms`, `Budget`, `Features`) con cortocircuito rápido ante descartes críticos.
* `src/services/blindMatching.ts` *(KAN-37)*: Motor de matching cross-tenant, dirección búsqueda→cartera del "matching ciego". `matchRequestAgainstProperties()` es función pura (reutiliza `checkMatch()` de `matcher.ts`, sin acceso a red) y `findCrossTenantMatches()` cruza el pedido de un tenant contra la cartera de TODOS los demás tenants con el cliente service-role (deliberado: el `req.supabaseClient` scoped de KAN-63 bloquearía por RLS la lectura cross-tenant que esta feature necesita), excluyendo la cartera propia vía `.neq('tenant_id', tenantId)` explícito en la query. Consumido por `POST /api/search` en `src/index.ts`. **Fix QA (2026-07-28):** `mapDbRowToProperty()` (exportada) reconstruye `zone_display_name: row.sheet_name` al rehidratar un `Property` desde una fila de `properties` — faltaba, y sin eso `ZoneMatchingStrategy` (`utils/matcher.ts`) rechazaba sistemáticamente cualquier búsqueda con zona. Mismo patrón que ya usan `src/index.ts#main()` y `src/services/whatsapp.ts` para el mismo problema (campo runtime-only, no persistido en BD).
* `cache/`: Directorio reservado e ignorado en Git para almacenar archivos JSON de sesión, configuraciones temporales de grupos y logs locales de ejecución.

## 4. Robustez y Seguridad
1.  **Idempotencia:** Control estricto en `coordinator.ts` mediante el ID único nativo de WhatsApp para evitar reprocesamiento y doble gasto de tokens.
2.  **Sincronización Atómica:** El proceso de carga de propiedades desde Excel/Sheets realiza un algoritmo de diferenciación (Updates/Inserts/Deletes) mediante `.upsert()` en Supabase para evitar ventanas de catálogo vacío.
3.  **Prompt Injection Shield:** Toda entrada de chat de usuario se inyecta a las APIs de IA envuelta en etiquetas XML estricta junto a instrucciones de inmunidad operativa del sistema.
